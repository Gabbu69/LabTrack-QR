# Real custodian sign-in

LabTrack follows the Thesis Scheduler account flow with **Custodian** as the staff role: create the named staff account, sign in with its own password, then verify an authenticator code. It keeps the existing Supabase authentication and database protections.

## Custodian steps

1. Open the private setup link supplied by the project owner. Check your name and email.
2. Choose a password with at least 10 characters, including a letter and a number. Enter it twice and press **Create custodian account**.
3. On Sign in, enter that email and password.
4. Press **Set up authenticator**. Scan the QR with Google Authenticator or Microsoft Authenticator. If using the same phone, enter the manual setup key in the authenticator app as a time-based key.
5. Enter the app's current six-digit code and press **Confirm authenticator**. Press **Create recovery code**, download it, confirm you saved it, then press **Continue**.
6. On subsequent sign-ins, enter the password followed by the current authenticator code. You do not enroll the phone again.

The account has the `custodian` role and `operational` data scope. It does not use the shared demo password or demo MFA exemption. The chosen password is private; it is not printed in chat or generated by the owner script.

## Project owner: prepare the named account's link

Get the intended custodian's name and real email. Staff account setup is not a public role picker. Create an ignored local request file, for example `output/private/custodian-request.json`, containing `name`, `email`, and `siteUrl`. Use `http://localhost:3000` for the local application. A production link only works after this revision is deployed there.

Run under Node 24 with the intended backend environment:

```text
node --env-file=.env.local scripts/create-custodian-invitation.mjs output/private/custodian-request.json
```

The command checks for an existing profile, then saves the private link in `output/private/custodian-setup-link.json`. It does not send email or create the account yet. The link expires after one hour and is bound to the approved name and email. Give it only to the intended owner; whoever holds it can choose the initial password for that named account.

The setup submission creates a new Supabase Auth user and operational custodian profile. It cannot overwrite an existing account's password, role, or authenticator. Reusing the link after account creation fails safely. Existing users must use their existing account and authorized recovery instead.

This owner-issued setup approves the account address administratively; it is not evidence that a confirmation email was delivered or inbox ownership was verified. Only the tool custodian creates student and staff accounts in User Management. Public sign-up is disabled. New users must verify an authenticator and replace their temporary password.

The invalid-link page is available at `/setup-custodian`; it shows instructions and cannot create an account without a valid owner-signed invitation. The invitation page uses private/no-store caching and a no-referrer policy.

## Recovery and verification

Save the one-use recovery code shown after setup. If the phone is lost, enter the account's sign-in details, choose **Use recovery code**, and provide the password and saved code. Recovery consumes the code, removes the lost authenticators and signs out. Sign in again and link a new authenticator before accessing the app.

Existing users can create or replace their recovery code through **Profile → Manage authenticators → Create recovery code**. This requires a verified authenticator session and replaces the previous code. Only its SHA-256 hash is stored in server-managed authentication metadata. All creation, consumption and factor changes share the existing per-user security lease; editable user metadata is never trusted. This application recovery mechanism uses the existing authentication service and requires no new paid service or database migration. A failed provider operation after consumption leaves the code spent and requires owner support; it never restores the code or grants portal access.

Keep a verified backup authenticator before changing phones. Custodian password resets do not remove authenticator protection.

Forgot the password but still have the authenticator? Choose **Forgot password?** on Sign in. Enter the email, current authenticator code, and a new password twice. The old password and email inbox are not needed. Sign in again with the new password and the still-linked authenticator. Incorrect codes, recently consumed reset codes and attempts against disabled or shared sample accounts are rejected. Anonymous reset attempts have separate account and network limits.

`MFA_CUSTODIAN_INVITATION=true` enables the real setup-form path in the existing disposable-account verifier, alongside `MFA_ALLOW_DISPOSABLE_ACCOUNT=true` and `MFA_REQUIRE_DATABASE_GATE=true`. It tests creation, replay rejection, real password sign-in, authenticator enrollment, AAL1 denial/AAL2 access, subsequent code entry, invalid-code rejection, device replacement, and cleanup. It must never enroll an existing client's authenticator.

`MFA_RECOVERY_WORKFLOWS=true` additionally tests the real code download, hashed storage, wrong-code/password rejection, one-use consumption, required QR re-enrollment and used-code replay rejection.
